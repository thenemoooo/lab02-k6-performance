## Stages туршилт (5→30→100→0 VU ramp)

`scripts/stages.js`-ээр 5→30→100→0 VU-г нэг ажиллуулалтад тасралтгүй
өсгөж бууруулсан. Үр дүн (results/run-stages.txt): p95=10.28s,
checks 99.3% амжилттай (1 алдаа гарсан, 144-с). Тогтмол VU-гийн
тестүүдтэй (p95≈230-270ms) харьцуулахад p95 хамаагүй өндөр гарсан нь
ramp-up үе шатанд шинэ холболт үүсгэх (connection establishment)
ачаалал давхцаж, latency огцом нэмэгдэж болохыг харуулж байна.

## SLO сонголт ба тайлбар

Baseline p95 (1 VU smoke test, results/smoke.txt) = 271.6ms.

Иймд threshold-ийг **p(95)<408ms** (baseline × 1.5) гэж сонгосон. Мөн
error rate-ийн ерөнхий найдвартай байдлын шалгуур болгон **rate<0.01**
(1%-иас доош алдаа) сонгосон — учир нь healthy backend-д 1%-иас дээш
алдаа гарах нь ер бусын том асуудлыг илтгэнэ.

## PASS/FAIL үр дүн

- **PASS** — 30 VU дор: p(95)=234.29ms < 408ms, error rate=0% (results/slo-pass.txt)
- **FAIL** — 30 VU дор, threshold-ыг зориудаар хатуу (`p(95)<50`) болгосноор:
  p(95)=795.26ms ≥ 50ms тул FAIL, харин error rate=0% (server хэвийн ажилласан,
  зөвхөн threshold өөрөө хатуу тул FAIL гарсан — серверт хэт ачаалал өгөхгүйгээр
  FAIL-ыг харуулах зөв арга) (results/slo-fail.txt)

## Дүгнэлт

Ачааллыг 5-аас 100 VU хүртэл нэмэгдүүлэхэд p95 хариу хугацаа 274.96ms-с
232-234ms хооронд тогтвортой хэвээр байсан бөгөөд огт ямар нэгэн
доройтол ажиглагдаагүй. Throughput нь VU-тай шууд пропорциональ өссөн
(7.38 → 44.57 → 142.84 req/s), энэ нь тестийн 5-100 VU муж дотор сервер
хэвийн бус хэт ачаалалд орж эхлээгүй байгааг харуулна. Error rate бүх
гурван түвшинд 0% байсан нь test.k6.io демо сервер энэ хэмжээний
ачааллыг амархан даадаг болохыг баталж байна. SLO threshold-ийг өөрийн
хэмжсэн baseline (271.6ms) дээр үндэслэн 1.5 үржвэрээр (408ms) сонгосон
нь зохиомол биш, бодит хэмжилтэд суурилсан утга гэдгийг баталгаажуулна.
30 VU дор энэ threshold амархан PASS гарсан ч, VU-г 1000 хүртэл огцом
нэмэгдүүлэхэд систем жинхэнэ дарамтад орж p95 4.48 секунд хүртэл
өссөн бөгөөд error rate 4.52% болж, threshold бодитоор эвдэрсэн (FAIL).
Энэ нь тухайн серверийн "хямарлын цэг" 100-1000 VU хооронд аль хаа
нэгтээ байгааг илтгэж байна. Лаб-ийг гүйцэтгэхдээ ёс зүйн зааврыг
чанд дагаж зөвхөн test.k6.io зааврын дадлагын сайт руу л тест
хийсэн бөгөөд AI-аар үүсгэсэн скрипт бүрийн target URL-ыг ажиллуулахын
өмнө гараар шалгасан болно.

## Ёс зүйн мэдэгдэл

Энэ лабораторид ашигласан бүх load тест зөвхөн зааврын дадлагын
серверт (https://test.k6.io) чиглэгдсэн бөгөөд ямар ч бодит,
зөвшөөрөлгүй вебсайт руу тест хийгдээгүй болно.

## AI өнцөг: AI-аар k6 скрипт үүсгэх туршилт ба дүгнэлт

AI туслахад «нэвтэрсний дараа хайлт хийдэг хэрэглэгчийн scenario-г k6-аар бич» гэсэн хүсэлт өгөхөд шууд ажиллахад бэлэн скрипт гаргаж өгсөн хэдий ч хэд хэдэн анхаарах зүйлс болон алдаанууд ажиглагдсан. 

1. **Анхны ажиллагаа ба засвар:** AI нь бодит бус (`https://example-shop.com`) дур мэдэн зохиосон target URL санал болгосон тул ёс зүйн болон аюулгүй байдлын үүднээс зөвшөөрөгдсөн туршилтын орчин болох `https://test.k6.io` руу сольж засвар хийх шаардлагатай болсон. Түүнчлэн `test.k6.io` дээр `/api/login` болон `/api/search` зэрэг API замууд байхгүй тул статик хуудасны хүсэлт болгон өөрчилж байж ажилласан.
2. **Threshold ба Stages тохиргоо:** AI нь `options` дотор `stages` болон `vus`/`duration` параметрүүдийг нэгэн зэрэг давхар тохируулсан нь k6 дээр тохиргооны зөрчил (`warning`) үүсгэж, `stages`-ийн тохиргоо нь бусад утгыг нь давуу эрхтэйгээр дарж ажиллахад хүргэсэн. Мөн босго шалгуурын хувьд (`http_req_duration: ['p(95)<300']`) ерөнхий стандарт утга санал болгосон нь тухайн орчны бодит baseline-аас шалтгаалж өөрчлөгдөх шаардлагатайг харуулсан.
3. **Өөрийн бичсэн скрипттэй харьцуулах нь:** AI-аар скрипт бичүүлэх нь олон алхамтай хэрэглэгчийн урсгал (User scenario: login -> search -> sleep), check болон sleep функцуудыг бүтцийн хувьд хурдан гаргаж өгөхөөрөө давуу талтай байв. Гэвч код хэсэгт бодит бус endpoint ашиглах, параметрийн давхардал үүсгэх зэрэг техникийн дутагдал гаргадаг тул инженер өөрөө нарийн хянаж, test environment-д тохируулан засварлаж байж ашиглах нь чухал юм.
